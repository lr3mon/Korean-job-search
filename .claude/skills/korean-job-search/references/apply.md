# 현재 문항에 근거한 자기소개서·경력기술서

## 작성 전 필수 입력

1. 정확한 법인·직무·공고 URL·채용 회차와 지원 자격.
2. 현재 양식의 **문항 원문 그대로**, 질문 순서, 세부 요구, 최소·최대 길이.
3. 공백/줄바꿈 포함 여부, 문자/바이트 기준, 제목 포함 여부, 첨부 파일 규칙.
4. 직접 근거 장부와 지원자가 확인한 사실, 블라인드 금지 범위.

공개 JD에서 알 수 있는 내용과 인증 후 폼에서만 알 수 있는 문항을 분리한다. 실제 문항에 접근할 수 없으면 `official prompt/limit unverified`로 표시한다. 과거 문항을 재현하거나 임의 제한을 넣고 “제출용 완성본”이라고 부르지 않는다.

```text
python3 -m korean_job_search prepare --job JOB_ID --jobs workspace/jobs.json --profile workspace/profile.json --out workspace/applications/JOB_ID
```

실제 ID와 경로를 사용하고 생성된 패킷을 읽는다. CLI가 만든 골격은 글쓰기와 사실 검증을 대신하지 않는다. 이미 있는 승인본을 덮어쓰지 말고 버전을 남긴다.

[문항 기록 형식](../templates/question-record.json)의 필드 정의를 참고해 현재 질문만 추가한다. 질문 원문·제한·확인 시각·출처·답변 파일·검토 상태를 하나의 기록으로 관리한다. 모르는 값은 `null` 또는 `unverified`로 둔다.

## 구조화된 사실을 먼저 정리한다

경력·교육·활동·자격·어학·프로젝트 란이 있다면 확인된 기관명·기간·역할·산출물부터 정리한다. 이 단계는 **로컬 초안**이며 온라인 입력을 뜻하지 않는다. 해당 사항이 없으면 빈칸으로 두고 필요 이상의 민감정보는 넣지 않는다.

경력기술 문장은 `문제/과제 → 본인 행동·대상·방법 → 확인 가능한 결과`로 쓴다. 회사 전체 성장·매출·트래픽을 개인에게 귀속하지 않는다. 비용·기간·비율 계산은 실제 근거와 계산 도구로 확인하고 분모·기간·범위를 표시한다. 숫자가 없으면 확인 가능한 산출물과 운영 변화만 쓴다.

## 질문마다 프레임을 고른다

| 문항 | 전개 | 반드시 보일 증거 |
|---|---|---|
| 문제 해결·직무역량 | 짧은 배경 → 판단 → 행동 → 결과 → 성찰 | 대안 비교, 본인 범위, 결과 출처 |
| 실패·도전 | 실패 신호 → 원인 가설 → 판단 수정 → 재실행 → 남은 한계 | 실제 실패, 바뀐 행동, 미해결도 정직하게 |
| 협업·갈등 | 상호의존성 → 목표/정보 불일치 → 조정한 접점 → 합의·결과 | 문서·기준·회의·책임 경계에서 바꾼 것 |
| 지원동기 | 회사의 확인된 과제 → 직무 이유 → 닮은 경험 → 첫 기여 방식 | 공식 사업 사실과 본인 경험의 구체적 연결 |
| 장점·약점 | 실제 성향 → 발생한 장면 → 결과 또는 통제 장치 | 실제 행동, 이후 확인된 변화 |
| AI 활용 | 병목 → 입력/출력 → 도구 선택 → 검증·예외 → 적용 결과 | AI가 한 일과 본인이 설계·확인한 일의 구분 |

STARR/PAR는 사고 도구다. 최종 문장에 S/T/A/R 라벨을 남기지 않는다. 성찰은 “중요성을 배웠다”보다 이후 실제로 적용한 확인 순서나 판단 기준을 적는다. 그 변화가 실제로 없으면 새 과거 사실을 만들지 말고 앞으로의 계획이라고 밝힌다.

## 초안의 순서

1. 첫 두 문장 안에서 문항에 답한다. 핵심 주장 하나와 대표 경험을 고른다.
2. 상황 설명을 줄이고 **무슨 신호를 보고 왜 그 방법을 선택했는지**를 쓴다.
3. “저는/제가”가 필요한 곳에서는 남겨 개인 기여를 명확히 한다. 역할–대상–방법–산출물을 연결한다.
4. 팀·회사 결과와 본인 행동을 별도 문장이나 범위 표시로 분리한다. 전후 비교가 아니면 개선율이라고 부르지 않는다.
5. 결과의 의미와 한계를 설명하고 실제 성찰을 직무에 짧게 연결한다.
6. 문항별 대표 경험·수치·역량 배치를 표로 비교한다. 한 경험을 재사용할 때는 같은 설명을 복제하지 말고 질문이 요구하는 다른 증거를 사용한다.
7. 구조와 사실을 고정한 뒤 자연스러운 한국어로 국소 윤문한다. 군더더기·공통 칭찬·“이를 통해” 반복·근거 없는 자기평가를 줄인다.

정중한 문체를 유지한다. 리듬을 바꾸려고 새로운 감정·동기·갈등을 넣거나 전문 용어·도구 버전을 일반화하지 않는다. 기존 초안을 고치는 요청이면 승인된 경험·수치·명칭을 보존한 작은 수정을 우선한다. 사용자의 최신 부분 수정이 과거 초안으로 되돌아가지 않게 비교한다.

## 블라인드 채용

현재 공고의 금지 정보 목록을 인용해 체크리스트로 만든다. 학교명, 출신지, 성별, 연령, 가족, 사진 등의 금지 범위는 기관마다 다르므로 일률적으로 가정하지 않는다. 학력 요건 확인용 비공개 증빙과 제출 본문을 분리한다.

본문뿐 아니라 파일명·머리말·PDF 속성·포트폴리오 링크의 노출도 검사한다. 익명화로 문장을 바꿔도 사실·역할·기간을 바꾸지 않는다. 경력 기관명 공개 가능 여부가 불명확하면 확인 필요로 둔다.

## 정확한 길이 검증

UTF-8 텍스트 파일에 답변 **본문만** 저장하고 다음을 실행한다.

```text
python3 -m korean_job_search answers-check workspace/applications/JOB_ID/answers/q01.txt --limit LIMIT --mode codepoints
```

실제 제한으로 `LIMIT`를 바꾸고 모든 답변에 실행한다.

- `codepoints`: Unicode 코드 포인트 개수. 눈에 보이는 글자(자소 결합·이모지) 수와 다를 수 있다.
- `utf16`: UTF-16 코드 단위. 일부 브라우저의 문자열 길이와 대응하지만 실제 사이트 구현을 확인한다.
- `utf8-bytes`: UTF-8 바이트 수. 한글·기호가 같은 바이트라고 가정하지 않는다.
- `cp949-bytes`: CP949 바이트 수. 인코딩 불가능한 문자 오류를 무시하거나 `?`로 바꿔 계산하지 않는다.

공백·줄바꿈·CRLF/LF·최소 길이를 정확히 기록한다. CLI 기본 계산과 사이트 규칙이 다르면 그 차이를 표시하고 실제 규칙에 맞는 별도 계산을 도구로 수행한다. 지원하지 않는 CLI 옵션을 지어내지 않는다. 본문의 줄바꿈·Unicode 정규화·말미 개행을 조용히 바꾸지 말고 계산 조건을 남긴다. 최대 한도만 통과해도 최소 길이를 충족했는지 따로 확인한다.

검토된 본문과 계산한 파일은 같은 버전이어야 한다. 원문을 붙여넣은 온라인 카운터를 확인할 수 있다면 사용자 승인 범위 안에서 값만 비교한다. 실제 양식의 카운터·오류가 최종 기준이며 차이가 있으면 완료로 처리하지 않는다. 외부 저장·입력·제출은 이 스킬의 기본 범위가 아니다.

## 인계

질문 원문 → 최종 초안 → 실제 계산 결과/제한/모드 → 경험 출처 → 미확인 사실을 문항별로 보여준다. 작성 완료, 검토 완료, 온라인 저장, 제출 완료는 별개 상태다. 남은 글자를 추상적 포부나 만든 수치로 채우지 않는다.
